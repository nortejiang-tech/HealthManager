# HealthManager：营养表增删、可信搜索与可编辑推测配方

> 日期：2026-09-18｜增量需求，基于已使用的 v0.6.0。
> 交付对象：ZCode。本文是开发方案，没有修改 App 源码、运行数据库或 GitHub 仓库。
> 与 2026-09-17 文档的关系：沿用已交付导航和营养表布局；本轮关于目录维护、在线检索、配方推测的规则优先于上一轮“仅离线目录/空白新建配方”的范围限制。

## 1. 已确认需求与本轮边界

用户已明确确认：

1. 参考食材支持删除；含义是从个人营养表移除，之后可搜索并重新添加，以前的饮食和配方不受影响。
2. 支持输入食物名称，从可信资料库检索对应营养后添加；名称有差异也应能够找到。典型场景是搜索“黑巧克力”。
3. 我的常吃中，先以官方食材生成可编辑的推测配方；用户可以修改，确认后保存为常用版本。

产品目标：查食材更完整、列表可整理、常吃菜不用从零填配方；继续保持功能精简、数值可信、操作直观。

本轮不重新调整选项卡、不重做趋势页、不加入健康评分、不要求用户逐项填写微量营养。手动添加在本轮指“输入名称并选取可信数据条目”，不是随意填一组数字再标为官方数据。

## 3. 页面和操作方案

### 3.1 参考食材：维护“我的参考表”

保留现有“参考食材 / 我的常吃”切换。参考食材右上增加“＋”，列表支持左滑“移除”，详情菜单提供同一操作以便发现。

- 点击移除后立即隐藏，短暂显示“已移除 · 撤销”；这是可逆操作，不再反复弹确认。
- 移除只改变个人列表成员状态，不删除官方资料，也不删除旧饮食和配方引用的数据。
- 搜索框仍筛选当前参考表；“＋”进入完整资料搜索。无结果时提供“搜索资料库并添加”。
- 全部移除后的空态：“还没有参考食材”，主按钮“添加食材”。
- 在添加页搜到已移除条目时显示“重新添加”；已经在表中的显示“已添加”。
- 恢复同一条目不产生副本；App 重启、升级、备份恢复后不自动把移除项塞回来。
- 官方目录的可检索范围与个人列表分开。隐藏的条目仍可用于旧配方；在配方选择器使用它，不默认恢复到个人参考表。

### 3.2 添加食材：输入名称 → 选择候选 → 查看营养 → 添加

单个弹出页完成，不增加顶级页面。示意布局如下；候选名称只说明交互，不代表本文已经验证了这些条目的营养值。

> 添加食材　　　　　　　　　取消  
> 搜索食物，如黑巧克力　　　　　  
> 本地结果先显示；提交后继续查询资料库  
> 黑巧克力 · 可可含量 70–85%　来源/类型  
> 黑巧克力 · 其他可可含量　　 来源/类型  
> 点选后：每 100 g 热量、蛋白质、脂肪、碳水  
> 来源详情　　　　　　　　　添加到参考食材

具体行为：

1. 输入时立即查本地目录和已导入资料；按键盘“搜索”后查询官方远端，不对每个按键都发请求。
2. 同一搜索会话合并去重本地和远端结果，先保留强匹配。返回上一页时保留查询和滚动位置。
3. 候选必须展示区分食品所需的限定词：可可含量、生熟、是否加糖、品牌等。名称过长允许两行，不只显示相同的“黑巧克力”。
4. 点选候选后取完整详情，显示每 100 g 的能量 kcal、蛋白质 g、脂肪 g、碳水 g；纤维、钠和更多出处折叠。
5. 只有详情已取得、来源身份和计量基准明确时才能添加；搜索摘要不能冒充完整营养记录。
6. 添加写入持久化资料和个人表成员状态后再提示成功，返回原列表并定位新条目。重复点击保持幂等。
7. 可编辑个人显示名和别名，例如将官方译名改为“常买的黑巧”；原始名称、来源和营养值不因此改变。

“黑巧克力”只定义一类食品，不能自动选第一个结果替用户决定可可比例。用户选择之后，列表名称保留区别，例如“黑巧克力（70–85% 可可）”。若找到的是饼干、夹心糖或巧克力饮料，应降低排名并清楚显示，不能当作普通黑巧克力添加。

### 3.3 模糊搜索规则

按顺序扩大候选，而不是放宽营养可信要求：

- 规范化：空格、大小写、全半角、常见标点及繁简差异；保留数字、百分比和否定词。
- 名称与别名：黑巧 / 黑巧克力 / dark chocolate 等维护可追溯别名；输入 typo 可给近似词。
- 关键词和词序：用词项匹配覆盖官方长名称；比普通 contains 更宽容。
- 跨语言：中文查询生成官方资料库支持的检索词；优先本地词典，已有文本模型可辅助翻译。模型输出仅用于搜索词，不能输出营养值作为检索结果。
- 排序：食品身份和加工状态吻合优先，再比较数据来源与名称相似度。用户明确输入 85% 时，不把不符合含量的条目当完全匹配；“70–85%”是范围，不能改写成测得的“85% 专属值”。
- 模糊程度较高时标记“可能匹配”，仍由用户选取；无可信候选时如实无结果，允许换关键词。

验收需同时覆盖中文原词、别名、英文、轻微错字、限定词和误匹配排除；不能仅靠为“黑巧克力”写一条特例过关。

## 4. 可信资料库与联网边界

### 4.1 建议的首版来源

保留已有 MEXT 离线目录，增加一个 USDA FoodData Central 检索适配器。先把一个新增来源的获取、显示和保存做完整，避免同轮拼装多个不稳定网页爬虫。

USDA 提供官方搜索和详情 API，接口需要 data.gov API key，数据采用 CC0；生产使用不依赖低额度 DEMO_KEY。详见 [USDA API Guide](https://fdc.nal.usda.gov/api-guide/)。

来源类型必须说清楚：Foundation 是分析数据；SR Legacy 是历史汇编；FNDDS 是膳食调查相关汇编；Branded 来自厂家标签，不应全部显示成“官方实测”。详见 [USDA 数据类型说明](https://fdc.nal.usda.gov/data-documentation/)。

首版建议默认使用 Foundation、SR Legacy、FNDDS 通用食品；品牌标签检索可后续扩展。优先匹配正确食品，不能因为某类型排名高而把生食代替熟食。现有 MEXT 条目继续显示自身版本与出处，不能继承 USDA 元数据，反之亦然。

### 4.2 个人 App 的接入建议

建议使用个人 USDA key，在“更多 → 设置 → 食材资料库”一次配置并存入 Keychain；与 LLM key 独立，不能复用。未配置时显示本地结果并给出一次明确的配置入口。配置好后日常添加不需要额外操作。

这是本方案的技术建议，并非用户已指定 API 方案。如果开发电脑已有合规的官方离线全集和查询索引，可用同等能力的本地检索替换远端，但必须满足开放词汇搜索，不能把新增需求缩减成原 41 条搜索。若将来公开分发，再单独设计服务端代理；本轮不引入自建后端。

key 不写入仓库、日志或备份，不写死一个共享 key 到安装包。资料库服务不可用时保留本地搜索；已添加条目和已有配方可离线使用。需要联网的首次检索和推测应明确区分，不用一条“未找到”掩盖未配置、超时或限流。

### 4.3 数据映射硬要求

- 用来源 nutrient ID、单位和官方定义映射能量/蛋白质/脂肪/碳水，不靠字段排列顺序或模糊中文标签。
- 同时出现不同能量口径时，适配器定义并记录选择规则；不相加、不由模型任选。保留原能量值，不能默认用 4/4/9 覆盖。
- 每份标签不能直接当作每 100 g；无法建立计量基准时，不显示假定的百克值。
- per100mL 与 per100g 分开显示。没有可靠密度或明确换算依据时，不能把 mL 当 g 进入配方。
- 未测量/缺失显示“—”，trace 与 0 区分；不把字段缺失补为零。缺少一个营养字段不妨碍其他已知字段展示。
- 保存 provider、原始 food ID、原名、数据类型、来源版本或发布信息、抓取时间、条目 URL、计量基准、营养值及质量标记。无官方版本号时以抓取时间和内容摘要识别快照，不伪造版本。
- 加入“零食 / 甜食”或兼容的“其他”分类，保证历史枚举和备份能解码；不要因新增分类阻断导入。

本文不提供未经官方详情核验的巧克力数值。开发验收时须选定真实官方条目，保存可复核的详情样本和字段映射证据。

## 5. 我的常吃：先给配方，再允许修改

### 5.1 入口与优先顺序

沿用当前历史频次候选，不重新设计常吃识别：

1. 已有本人确认配方：打开已有版本编辑，不自动重算或覆盖。
2. 能直接匹配单一官方食品：提供官方匹配，允许用户改选。
3. 复合菜或需拆解的候选：将“补充配方”升级为“生成参考配方”，点击后生成并进入现有编辑器。

这里的“先推测”指新建配方不再一张空表；不意味着每次进入页面都批量调用模型。首次生成成功即展示内容，用户不必先回答所有克数问题。生成失败时保留“手动建立配方”入口。

### 5.2 生成过程和可信边界

处理链：历史名称及有限上下文 → 推测原料组成 → 匹配官方原料 → 推测克数、用油和成品重量 → 本地计算 → 可编辑初稿。

- 只使用当前菜名、相关已记录的食材/份量、用户之前确认过的匹配等必要信息。明确的历史值优先，但历史 AI 估计不能升级成称重事实。
- 模型可以建议原料、比例、用油及出锅重量；这些数字标成“推测”。官方原料的营养值只能由资料适配器返回。
- 先提取待查原料，再把已解析的官方候选交给配方生成；模型只能引用给定候选 ID。服务层校验 ID、数值有限且非负、单位、状态、数量边界和字段完整性。
- 只保留一个最合理初稿，不一次给用户多套长方案；解释只需一句，例如“按常见家常做法推测，油量和成品重量可调整”。
- 不把模型建议的原料克数反写成历史事实，不修改旧餐次。
- 找不到某原料时，保留“待匹配原料”一行，允许选择/替换/删除，不能悄悄略去。受影响的营养总量标记不完整，不能呈现成完整百克营养。
- 资料取得失败与模型生成失败分别处理；保留已经匹配和用户已经修改的内容。
- 调用已有文本模型配置；只发送该次配方必要信息，不上传整个饮食库、用药或 HealthKit 数据。首次说明联网推测的用途，后续同范围操作不反复打断。

### 5.3 编辑器

标题“推测配方”；主按钮“确认并保存”。固定可见内容为：菜名、原料列表、成品总重量、每 100 g 结果。以下操作必须保留或补齐：

- 添加、移除、替换官方原料；查看每项所用数据来源。
- 修改原料用量、生熟对应条目、用量状态；修改菜名、备注。
- 油单独列出，可改克数、标注不用或未知，不能藏在一个不可修改的模型总数里。
- 修改成品重量及其依据，允许称重值替换推测值。不能默认用原料总重代替熟食出锅重量。
- 编辑后立即重新计算；“已称重 / 估计 / 未知”沿用现有语义。改一个数字并不自动变成已称重，需要用户明确标记。
- 点击重新生成时先保留当前草稿，展示新草稿供应用；不能覆盖用户未保存的手工修改。
- 退出时沿用草稿保护；取消不得产生已确认配方或修改历史。

“确认”是用户接受当前参考配方，不会让它变成官方菜品或实测营养。保存后标记“个人配方 · 含推测用量”，手动修改后仍按实际依据显示。只有相关字段确实经称重，才能显示相应称重依据。

可以保存不完整草稿供稍后处理；成品重量未知/≤0 或关键原料未匹配时，不得发布可用于记录的完整百克版本。不可用字段给出具体缺项，不以 0 代替。

### 5.4 计算规则

对于以克计且具有每 100 g 数据的原料：某项营养总量 = 各原料该项百克营养 × 原料克数 ÷ 100 的和；成品该项百克营养 = 总量 ÷ 成品可食重量 × 100。

营养和克重沿用食材的可食部基准。原料重量与条目的生熟状态必须一致；不能把生米值套在熟饭克数上。用熟制条目就不再重复套一遍烹调损失。没有明确保留率、弃汤或吸油依据时，把结果称为参考估算，不能暗示已经精确模拟烹饪。水影响成品重量；用油量应体现进入可食成品的估计量，不能无条件把锅中全部投油算作吃下的油。

存在未知量时按营养字段传播不完整状态；已知小计若展示，必须叫“小计”，不能替代完整合计。成品重量需是正的有限数。计算保留内部精度，仅显示时舍入；无依据的置信百分数和精确范围不展示。

## 6. 数据设计：先保证删得安全、算得稳定

具体类型名由 ZCode 顺应仓库决定，下表是必须满足的合同，不要求照抄表名。

| 层次 | 持久化内容 | 修改原则 |
|---|---|---|
| 官方食品身份 | provider + 官方 food ID，原始名称 | 中文别名不同不能生成重复身份 |
| 官方资料版本 | 计量基准、完整营养、出处、版本/时间/摘要 | 不可变；更新产生新版本 |
| 我的参考表成员 | 官方身份、选用版本、显示名、active/removed、修改时间 | 移除是状态变化，重新添加恢复成员 |
| 个人配方版本 | 每项原料资料快照/不可变版本引用、克数与依据、成品重量与依据、来源说明 | 保存修改生成新版本，旧版保持 |
| 配方推测草稿 | 未确认字段、待匹配项、生成依据和手工修改 | 未确认不用于完整百克记录 |

原料快照至少能独立还原当时的每 100 g/100 mL 营养、质量标记和出处；不能只保存 catalogEntryId + catalogVersion 再读取“当前目录”。可选嵌入快照或引用随备份导出的不可变版本，但必须通过离线恢复测试。

必须修复 RecipeEditorView 的 unresolved 跳过路径及 MyFrequentPanel 的 compactMap 漏项路径：无法解析的项保留并阻止误导性完整结果。移除表成员不应导致解析失败；真正损坏/缺失也不能默默降总量。

更新官方数据时，旧配方/旧餐次仍使用旧快照。对个人表可提示有新版本，显式采用；更新当前参考值不自动升级历史配方。用户若想升级某配方，另存新配方版本。

### 6.1 升级与备份

当前仓库已至 v9 数据库迁移与备份格式 2；开发时核实最新序号，追加迁移，不修改已执行迁移。建议新备份格式升级为 3，并更新格式合同。

- 老目录的 41 条默认初始化为个人表 active 成员一次；后续启动不重新初始化成员。
- 为现有配方补快照时仅使用可确认的原版本资料；当前目录不同版不能冒充旧版。无法恢复的明确标记待修复，保留原数据。
- 新备份包含个人表成员及移除状态、导入的官方资料/版本、个人显示名与别名、配方快照及版本；缓存可不导出，已添加资料绝不是缓存。
- 恢复格式 2 时兼容旧结构并执行迁移；格式 3 的新字段需有明确校验。恢复须按实际外键依赖在事务内完成，失败回滚，不能留下半套配方。
- 同一备份重复恢复不产生重复条目；以稳定身份去重，不能按中文名称去重。
- 沿用 App 现有恢复模式；若有合并恢复，同身份成员以明确的版本/修改时间规则解决 active/removed 冲突，不能无条件 active 覆盖 removed。
- 不导出 key；旧 App 若不支持格式 3 应明确拒绝，不能假装成功后丢失新增内容。

## 8. 验收清单

### 8.1 必须自动化覆盖的行为

| 编号 | 场景 | 通过标准 |
|---|---|---|
| D1 | 移除被旧配方使用的原料 | 列表消失；旧配方及旧餐次数值不变 |
| D2 | 移除→重启→备份恢复→搜索重加 | 移除状态持久；可恢复；无重复成员 |
| D3 | 移除全部默认条目后升级 | 正常空态；默认条目不自动复活 |
| S1 | 名称/别名/英文/错字搜索 | 正确候选可发现；候选身份仍为官方 ID |
| S2 | 黑巧克力与黑巧克力饼干 | 区分食品类型和可可含量，不悄悄选首项 |
| S3 | 选择真实官方详情并添加 | 数值、单位、基准及出处与保存的官方样本一致 |
| S4 | 断网、未配 key、401、429、超时 | 明确状态；本地仍可用；不生成虚构数据 |
| S5 | 快速重复添加、搜索晚返回 | 一条持久记录；过期响应不覆盖新查询 |
| N1 | null、trace、0、每份与每 100 mL | 语义保持；无未经依据的克/毫升转换 |
| R1 | 常吃复合菜生成初稿 | 包含可编辑原料、用油和成品重量依据；推测标识明确 |
| R2 | 改油量/原料/成品重量 | 数值即时随确定性公式变化；保存为新版本 |
| R3 | 模型编造 ID、非法数量或原料未匹配 | 校验拦截；不跳过后输出完整总量 |
| R4 | 手动编辑后重新生成或取消 | 原草稿受保护；取消不污染正式版本 |
| V1 | 更新官方值或移除表成员 | 原配方版本数值稳定；新版本明确采用新值 |
| B1 | 旧格式升级＋新格式导出导入 | 可离线完整恢复新增食材、移除状态与配方版本 |

计算测试用虚构数值验证公式，避免把测试值当官方营养：若原料 A 每 100 g 为 100 kcal，用 200 g；原料 B 每 100 g 为 900 kcal，用 10 g；成品 250 g，则总量 290 kcal，百克为 116 kcal。把成品改为 300 g 后应显示约 96.7 kcal/100 g；存在未知原料时不能仍把 290 当完整总量。该例不代表任何实际食物。

搜索/模型测试使用脱敏固定样本保证稳定；另做至少一次真实官方搜索与详情取回验证。远端不可用时记录未验收，不以模拟结果宣称线上集成通过。

### 8.2 真机验收

- 使用现有数据升级，默认入口、历史记录、原有个人配方正常。
- 三条主流程分别录屏或截图：移除并重加；输入黑巧克力并选择候选添加；常吃菜生成→改油量/成品重量→保存。
- 长中文名、数字列、深色模式、大字体可读；左滑按钮不影响纵向滚动；键盘不遮挡搜索/添加。
- 联网中显示轻量进度并可取消；返回列表后不丢搜索上下文，不突然覆盖用户选择。
- 检查来源详情可进入、离线可读快照、全空状态明确。
- 回归与本轮相关的现有测试，报告实际执行结果及未完成项，不沿用昨日通过数量作为本轮证据。
