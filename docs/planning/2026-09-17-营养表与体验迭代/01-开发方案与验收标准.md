# HealthManager：营养表、常吃食物与体验精简开发方案

> 日期：2026-09-17｜基线：v0.5.1（build 11）｜建议迭代：v0.6，版本号由开发时确定。
> 本次交付仅为分析与开发文档。没有修改 App、数据库、备份、GitHub 仓库，也没有执行发布。
> 阅读顺序：本文 → [官方来源与个人食物方案](02-官方来源与个人食物方案.md) → [饮食备份审计](03-饮食备份审计.md)。

## 1. 产品判断与本轮目标

这个 App 已有较完整的数据可信性基础，但日常使用仍需在较多说明、状态和页面之间寻找真正要做的事。下一轮应把核心体验收敛为：**打开看趋势，吃饭时快速记录，查食物时有可靠依据，同一种常吃食物不用反复猜。**

最值得做的不是更多 AI 分析或再设计一套健康评分，而是把现有“可信、可纠正”的能力变成更少的操作、更稳定的数值和更清楚的页面。

用户本轮已确定的需求：

1. 移除一级「今日」页，趋势移到最左并作为首页。
2. 原趋势位置新增「营养表」，展示每 100 g 热量、蛋白质、脂肪、碳水等。
3. 基础食材使用可靠官方来源，并能查看出处。
4. 从本人历史记录整理常吃食物；能以参考食材组合个人菜品，计算每 100 g 营养。
5. 功能精简、准确、好用、美观。本次不开发，交给晚上的 Agent 实现。

以下内容是开发建议，不等于已实现：离线目录、个人配方、历史搜索、主页精简、质量告警分组。应按第 10 节逐阶段落地，避免一次重写整个 App。

- 换 Tab 只读数据，不生成餐次、不触发 HealthKit 营养写入、不发起 AI 请求。

## 4. 营养表页面

### 4.1 页面结构

使用一个页面内的两段切换：「参考食材」「我的常吃」。首次进入默认“参考食材”，以后记住该页内上次选项。避免再叠一层底部导航。

从上到下：

1. 标题「营养表」，旁边一个轻量的来源说明入口。
2. 搜索框：可搜中文、已审核别名；保留原文名供详情核对。
3. 两段切换。
4. 「参考食材」中一行分类筛选：全部、主食、蛋奶豆、肉鱼虾、蔬果、油脂调味。
5. 固定说明「每 100 g 可食部分」。每一行显示食物名、生熟/加工状态、热量大数，第二行显示蛋白质/脂肪/碳水。
6. 点一行进入详情；详情底部主按钮「加入饮食」，进入草稿。

行样式示意（下列数据是真实官方条目，非本人米饭实测值）：

> 白米饭 · 熟 · 日本短粒粳米　　　　156 kcal
>
> 蛋白质 2.5 g　脂肪 0.3 g　碳水 37.1 g
>
> 每 100 g · MEXT 2023

来源为[文部科学省条目 01088](https://fooddb.mext.go.jp/details/details.pl?ITEM_NO=1_01088_7)。此示例不应简化成“所有白米饭固定 156 kcal”。具体来源、品种与做法在详情保留。

手机默认使用整齐行列表，不把 8 个营养字段硬塞进横向大表格，也不把每个食物做成大图卡。详情才展开纤维、糖、钠等。首版未核实的扩展营养素显示“—”。

### 4.2 食材详情与份量换算

- 默认基准每 100 g；支持输入本次可食重量，实时算本次营养。
- 同时显示“每 100 g”和“本次 X g”，避免改重量后误以为参考值变了。
- “一个鸡蛋”“一杯豆浆”只能来自可靠条目份量或本人确认过的换算；没有换算时要求填克数，不暗设每碗 150 g、每杯 250 g。
- 饮料保留原始 100 mL 口径；只有已知密度才换 100 g，否则明确显示 100 mL，不能悄悄当作等价。
- 显示出处机构、食品编号、原名、版本、生熟状态、可食部口径与“查看来源”。翻译名称不是新数据源。
- 默认显示官方已发布能量；不以 4/4/9 强行覆盖官方值。营养定义与能量计算法不同可产生差异。
- 对零、未知、微量、低于检出限分别处理，不把来源的 “-”“Tr” 都转换成 0。
- “加入饮食”只创建待保存草稿，可选餐次、时间、重量；最终点保存才走现有持久化与 HealthKit 流程。

### 4.3 我的常吃

显示三种清楚区分的条目，但不再增加三个独立页面：

| 类型 | 展示 | 允许动作 |
|---|---|---|
| 已匹配的常吃单品 | 官方参考值＋“近30天记录 N 餐” | 调整克数、加入饮食、置顶 |
| 我的配方/固定餐 | 配方估算＋版本；固定餐默认每份，详情可看每100g | 调整份量、编辑配方、另存版本、加入饮食 |
| 待确认候选 | 食物名称＋“待确认食材/做法”，不显示伪官方值 | 匹配、补充配方、忽略 |

候选自动出现，不要求第一次使用先填写几十张表。先展示真实常见项，让用户在需要使用时确认一次。被忽略的候选不要每次刷新重现。

## 5. 历史整理与配方计算合同

### 5.1 常吃统计

- 用 `meal_records.eaten_at` 的本地自然日统计，不按创建时间；本次审计采用 Asia/Shanghai。
- 产品默认近 30 个自然日；另有全部历史。分析本次备份的窗口为 2026-08-19～09-17，99 餐。不能悄悄以最后有记录日替代“今天”：如果产品数据已过期，要显示窗口与截止日期。
- 每食物每餐只计一次；排序为置顶优先，其后记录餐数降序、最近食用时间降序、稳定名称/ID打破平局。首版无需不透明评分模型。
- 计数是“记录中出现的餐数”，不是准确的实际食用次数。
- 别名匹配保留做法、品牌、口味、生熟。煮鸡蛋/白煮蛋可归并为候选；豆浆/无糖豆浆、玉米/煮玉米、干豆腐/豆皮/腐竹不能仅凭字面强行合并。
- 字符规范化可复用已有身份处理；语义等价采用小型可审查别名表。AI 只能建议匹配，不能提供假食品ID或自动决定模糊归并。
- 无分项、有备注的 43 餐生成独立待确认候选；不同时重复统计分项和备注。无食物信息的历史餐保留原总量，不凭热量猜菜名。
- 编辑/删除餐次后刷新频次；不持久化一份会与历史脱节的固定排行榜。缓存可重建。

### 5.2 食物与组合的边界

“无糖豆浆＋煮鸡蛋”是固定餐；“干豆腐卷大葱”是复合菜。两者可复用同一计算基础，但固定餐以每份展示更直观，饮料不能通过增加重量让整个早餐的每百克数值被误解为更健康。

个人菜品不能拿多次 AI 的 kcal/100g 做平均后冠以官方来源。只有匹配到真实食材条目，并掌握相应重量与做法，才产生“基于官方食材计算”的版本。

### 5.3 计算规则

令 Nᵢ 为某食材每100g的某营养素，wᵢ 为与条目状态相同的可食重量：

- 同状态食材贡献 = Nᵢ × wᵢ / 100。
- 菜品总营养 = 各项贡献之和，并按适用的烹调保留/流失调整。
- 菜品每100g营养 = 菜品总营养 × 100 / 最终可食成品重量。

原料生重、熟食条目不能直接混用。若用生料计算熟菜，需要实测成品重或有出处的出成率；失水增浓、吸水稀释、油脂吸收与弃汤都应按适用情况处理。已使用熟食条目时，不再对同一部分重复套烹调系数。方法依据见附件中的 FAO 原始资料。

首版支持两种模式：

1. **明确同状态组合：** 已熟食材按实际重量组合，适合早餐和无需再烹调的组合。
2. **自定义烹调配方：** 食材、用油与调味、成品总重可编辑。若缺可靠保留系数，明确采用简化估算及其假设，不显示“实测”。首版不推导维生素保留率。

缺失处理：某个食材某营养素未知，成品对应营养素也为未知；已知小计仅在详情中说明，不能当完整总量。成品重量未知时允许保存配方草稿，但每100g显示“待补成品重量”。重量为0、负数、非有限数时不能计算。

油、酱汁必须可表达“未使用（0 g）”“已称量”“估计”“未知”；未知用油不能按0处理。不要将来源本来已含油的熟菜与额外同一份油重复计入。

## 6. 从 UI 到功能的优化建议

### 6.1 优先级

| 优先级 | 改进 | 依据及收益 | 边界 |
|---|---|---|---|
| P0 本轮必做 | 趋势首页＋营养表＋常吃匹配/配方闭环 | 用户直接需求；稳定数值、缩短记录路径 | 不能只做只读营养列表就宣布完成 |
| P0 准确性 | 生熟、可食部、出处、配方假设、历史快照 | 全部分项状态未知；同名能量差异明显 | 不自动重算历史 |
| P0 数据安全 | 新个人配方与映射纳入备份恢复 | 当前备份只认识既有表 | 新能力不能升级后可用、重装后全丢 |
| P1 同期优先 | 饮食历史分页/搜索 | 实现只取最近50餐；已有326餐 | 复用已有餐次，不再建第二套记录 |
| P1 同期优先 | 合并重复说明、精简首页 | 源码中日期重复、摘要条与卡片重复、多个大说明区 | 保留来源能力，但下沉到就近详情 |
| P1 随后 | 个人份量与配方版本记忆 | 重复早餐、174条编辑标记 | 只记有确认范围的选择，不把改克数推断为改配方 |
| P1 随后 | 当前告警分组＋最近同步状态 | 历史告警数量多，运维状态对用户过重 | 分组不等于删除或全部确认 |
| P2 独立迭代 | Apple健康不可用时仍可查本地营养/记饮食 | RootView 当前整体门控主界面 | 需要单独验证授权与离线边界，不捆绑本轮基础改版 |
| P2 验证后 | 简短周回顾、本地交互指标 | 当前缺少使用行为证据 | 不新建聊天首页，不自动诊断或加目标 |

### 6.2 趋势首页：先回答“最近怎么样”

- 保留用户当前卡片顺序，沿用现有可隐藏与排序功能。不要把已有自定义布局又做一遍。
- 删除重复的日期和大段来源流程说明；页头只留一次日期、数据更新状态与编辑入口。
- 初版沿用原有卡片数据口径；下一阶段才把体重卡升级为近7/30天可切换的主趋势图。避免为视觉改版偷偷改能量算法。
- 最新体重明确标记实际测量日期；不是今天的数据就写“最近一次”，不写“今日体重”。
- 若加7日均值，用有测量的日值，显示有效天数；“较前7日”必须使用同长度窗口并说明缺失，不跨空白日硬连完整趋势。
- 热量缺口继续明确是基于已记录摄入的估算，不因分项字段齐全就推断全天饮食完整；缺必要输入时不制造精确缺口。
- 首页不同时放一排四个“今日大数”又在下面完整重复相同卡片。优先保留趋势图与进入详情的动作。
- “有 N 类数据待检查”替代长串历史红点数字；详情仍可看全部历史与原始告警。

### 6.3 饮食页：记录优先，说明按需展开

- 顶部短汇总显示“今日已记录”，不用“今日真实摄入”这类过度确定措辞。
- 主动作“记录饮食”；入口内提供拍照/文字/常吃，沿用现有编辑器与AI能力，不开发平行表单。
- 常吃列表能直接选择“早餐模板”，预填上次确认份量，改数量后本地计算，最终保存。
- 餐次按日期分组；日期筛选、菜名/备注搜索、逐页加载；查旧餐无需连续翻50条。
- 重复的“来源/本机/完整字段”说明缩成一个标签，点开详情才解释。出错或缺字段时就近指出具体缺哪项。
- 保留既有照片缺失占位。没有照片文件不代表当天没有拍照；此次备份本来不含照片。
- 菜名、克数、生熟、来源有一致的展示顺序，减少括号里堆品牌、推测和做法。

### 6.4 视觉语言：沿用现有风格，减少负担

继续使用现有 HM 设计系统、暖底色、系统中文字体和语义色，不另建一套主题。

- 每个页面一个主要动作；不要每段一个大标题、每个数值一个胶囊、卡片再套卡片。
- 营养行的名称左对齐，热量右对齐，数字使用等宽数字；kcal取整，宏量营养素通常保留1位小数。计算保持原精度，展示才舍入；非零小值不能一概显示成0。
- 官方参考是“有来源的参考”，沿用 comparison 语义；个人配方和AI显示估算语义。已保存状态与营养准确性分开，不用绿色勾让人以为称量或配方已验证。
- 默认字号横排；大字模式改为纵向营养行。支持深色、VoiceOver、减少动态效果；图标和颜色都不能是唯一信息。
- 减少大面积装饰、照片占位与首屏说明，让首屏看得到第一条数据和主动作。保留有用留白，不追求塞满所有指标。

### 6.5 怎样验证真的更好用

先用真机任务验收，不急着加入埋点SDK：

1. 打开 App 立即看到趋势。
2. 从营养表找煮鸡蛋、改150g、加入一餐，完整来源保留。
3. 复用常吃早餐、改豆浆份量、保存；不用重新调用AI。
4. 找到两个月前的一餐并进入编辑。
5. 解释一个菜品数值从哪里来、为何仍是估算。

记录每项是否完成、操作次数和耗时，改版前后同设备比较。若后续确需交互日志，优先本地聚合页面访问/搜索成功/草稿保存等计数；不记录食物正文、图片或健康原始数值，不默认上传。该日志建议不应阻塞本轮交付。

## 7. 数据与工程方案（规格，不是实现代码）

### 7.1 分开三类数据

| 数据 | 最小内容 | 性质 |
|---|---|---|
| 官方目录条目 | 稳定来源键、原食品ID、原名/中文名、食物状态、每100g值及缺失状态、来源链接、版本、字段定义 | 只读、可版本化的应用资源 |
| 个人映射与配方 | 原名映射、用户确认状态、置顶/忽略、默认份量、配方原料及来源版本、成品重量及依据、配方版本 | 用户数据，必须备份 |
| 已保存餐次分项 | 保存时的名称、重量、营养、出处和配方版本快照 | 延续 ADR-001；不能动态绑定最新版覆盖旧值 |

首版推荐随 App 打包30～50个经过核对的官方条目，实际数量以匹配准确为准。可用版本化JSON/资源数据库；不在手机上下载全量全球食品库，不让普通查询依赖联网。个人记录继续使用已有GRDB数据库。只有加入食物草稿和保存记录时才走写链路。

新增具体模块职责可为 FoodCatalog、FrequentFoodsQuery、RecipeCalculator、PersonalFoodStore；它们是拟议名称，不冒称仓库已有文件。不要为一个离线数据源先建设复杂Provider框架、远程后台或推荐服务。

### 7.2 关键字段合同

- 目录身份由“来源机构＋数据集版本＋原始食品ID”决定；不能用中文名字当唯一键。
- 分别保存“食材数值来源”“重量依据”“匹配是否已确认”“配方估算状态”，不能用一个 high confidence 代表全部可靠。
- 熟制状态、是否去皮去骨、是否沥干、是否加油/盐应可展示；无法确定时保留未知。
- 个人配方必须有不可变版本。修改配方生成新版本，旧餐继续引用旧快照。
- `meal_items`现有四个来源枚举没有 recipe_calculation。开发前补ADR，建议追加该来源值并更新解码、显示、导出恢复、测试，不能把配方伪装成 nutrition_database。
- 收藏或查目录不写餐次；配方修订不触发历史批量HealthKit改写。

### 7.3 迁移、备份与回滚

- 检查开发电脑实际迁移链，追加迁移，不修改已发布v1～v8；文件名与版本号以开发时现状为准。
- 新个人配方/映射的导出文件以及新增来源枚举意味着备份合同需明确升级。建议 formatVersion 2；新App兼容导入v1，旧App遇v2按既有策略明确拒绝，而非静默丢数据。
- 个人配方使用稳定ID，配方版本与原料引用先恢复，再恢复引用；重复导入幂等。目录条目若未找到，仍应显示餐次快照，不能丢餐或变0。
- 参考目录可由App资源重建，但个人配方依赖的原料数值/版本要随用户数据保留，以便以后资源包替换仍能解释旧配方。
- 保持已发布的用户表只补缺、投影表覆盖策略，不能照字段字典前部的泛化“只补缺”文字误处理所有表；以逐表规则及实现为准。
- 不卸载真实App进行首次调试，不以删除数据库解决迁移失败。先复制脱敏测试库验证；发布前备份真机数据。
- 数据库升级后回滚不默认能直接装旧版；新格式数据须由兼容版本读取，回滚方案应先验证。

## 9. 验收矩阵

| 编号 | 场景 | 必须满足 |
|---|---|---|
| A01 | 冷启动/后台恢复 | 冷启动趋势第一栏；后台恢复不丢编辑草稿；五栏顺序正确 |
| A02 | 升级导航 | 用户卡片顺序不变；既有更多入口、用药记录、同步恢复可达 |
| A03 | 官方参考 | 每个可用条目有真实ID、来源、版本、状态；无伪造值或模糊菜名自动匹配 |
| A04 | 份量比例 | 同状态100g→150g四指标按1.5倍；0/负/非有限重量拒绝；未知不变0 |
| A05 | 来源差异 | 官方能量与4/4/9不符时保留原值，不篡改官方能量；显示字段定义 |
| A06 | 饮料/可食部 | 不把100mL当100g；蛋壳、骨头、玉米芯不直接进入可食重量 |
| A07 | 配方 | 实测成品重变化能改变每100g，原料总营养不被水量凭空改变；油不重算 |
| A08 | 配方缺失 | 缺成品重量不可给每100g；缺任一原料某营养素时该总指标为未知 |
| A09 | 历史候选 | 分项和备注不重复计数；模糊做法需确认；删除餐次后频次更新 |
| A10 | 个人历史 | 新配方版本/目录更新不改变旧餐；没有把614条AI估算批量升级为官方 |
| A11 | 保存闭环 | 选食物→草稿→保存只生成一餐，沿用原HealthKit协调链；取消不写数据 |
| A12 | 离线与失败 | 无网照常查内置表、换算和记食；目录错误不显示假0；有旧内容则保留 |
| A13 | 备份 | v1导入不丢原记录；v2含个人配方/映射；重导幂等，校验失败不部分写入 |
| A14 | 历史查询 | 能搜到第51条以外餐次；分页不漏不重；后台查询不阻塞滚动 |
| A15 | UI | 明暗、大字、VoiceOver、减弱动态均可用；来源和状态不用颜色单独表达 |
| A16 | 真机发布 | 记录升级前后行数、历史快照、配方、卡片偏好、HealthKit写入结果；未通过不宣称发布完成 |

测试应验证合同与风险，而非为颜色或简单标签写镜像单测。重点为营养计算、生熟/密度、来源不可混淆、数据库迁移与备份幂等；UI测试覆盖少量完整用户流程。仓库旧测试数量是历史记录，不应作为本次已通过的证明。

## 10. 可交给 Agent 的实施顺序

### 阶段四：体验精简与发布

补历史搜索/分页、压缩重复说明与首页信息、当前告警分组。对比改版前后任务完成路径；保留既有趋势卡片偏好。完成A14～A16、回归和真机升级记录。
