01

一、起点：一句诊断，不是一份文档

HealthManager 没有留下一份类似"独立需求文档"的东西——第一轮提交（2026-05-13）就已经对照内部 PRD 直接交付了 12 张数据表结构，说明产品判断在写代码之前就想清楚了。真正的起点，是一句诊断和一条随之而来的产品纪律。

"健康数据分散在饮食记录、Apple Health、Apple Watch、运动 App、体重秤和热量计算工具里。数据不少，用户却仍然难以回答最日常的问题：今天摄入了多少？消耗了多少？当前热量缺口是多少？"
—— 项目自述「问题」

核心产品纪律：「不知道」≠「0」

任何一项输入未知时，宁可显式说明"当前不能计算热量缺口"，也不把未知静默补成 0 制造一个假的精确数字——这条纪律不是一句口号，本报告 §四 的 STAGE-007B 案例会展示它如何被系统性地落实到 7 条具体代码路径里。

四、关键难点全纪录

从 64 天里挑出最有代表性的技术难点——每一个都不是"改一行代码"式的小修补，而是带来了架构或纪律上的调整。

01

Round 8 的 MainActor 死锁：点完对账回仪表盘会卡住

05-14并发架构

现象

真机实测发现三类问题：回补/手动同步报错信息模糊；anchor 解码失败后同步无法自愈；点「立即对账」后回到仪表盘有概率卡住。

根因

SyncEngine 是 @MainActor，而四个 coordinator 当时是普通 class，因此继承调用方 actor——内部对数据库的同步读写调用直接卡死主线程；7 天对账 × N 个类型 × 数十次 SQL 会冻结 Dashboard 的刷新队列。

解法

四个 coordinator 全部改为独立 actor，SyncEngine 只保留 @MainActor 发布状态；DatabaseManager 新增 async 包装；anchor 解码失败改为自愈——捕获异常后清空该类型的锚点，下次自动走全量同步，而不是卡死在坏状态里。

02

跨源指标被错误相加：步数怎么比 Apple 健康多一倍

v0.2.x数据聚合

现象与根因

用户真机实测发现步数明显偏高。根因是 SummaryGenerator 对累计型指标（步数、距离、活动能量等）直接跨来源 SUM——Apple Watch 和 Garmin 各自记录的同一份运动事实被当成两份独立数据加总。

解法

引入 dominant-source 优先级策略：累计型指标按来源优先级只取一个主来源的值（用户明确要求"步数优先用佳明的"），非累计型指标（心率、体重）继续保持均值语义。单测锁定语义：Garmin 10000 vs Apple 8000 → 报 10000，不会 cross-sum 成 18000。

03

本地 AI 推理栈的两次不同失败：先错怪了客户端解析

06 月诊断方法论

第一层假设（错误）

"AI 摘要对思考型模型报 cannot parse response"最初被当作纯客户端 JSON 解析问题处理，代码加了容忍 content=null、剥离 <think> 块等逻辑——治标不治本。

真根因·第一层

服务端日志显示 oMLX 0.4.1 存在 VLM 崩溃回归（There is no Stream(gpu, 1) in current thread.），返回 500 被 App 误判为解析失败。解法：降级到 oMLX 0.3.12。

真根因·第二层（降级后才暴露）

oMLX 0.3.12 存在提示词缓存 bug——重复请求同一个大 system prompt 时命中缓存但返回空内容（completion_tokens=0）。用完全相同的 prompt 直接对本地服务器发请求复现后才定位到。解法：给 system prompt 加唯一 nonce 强制 cache miss。

教训

项目自己的复盘原话："未来调试应先查服务端日志，而非假设只是客户端解析问题"——这条经验后来被沿用，避免同类现象被反复误判为客户端 bug。

STAGE-007B：把"不知道≠0"钉进 7 条代码路径

07-14数据完整性

审计发现

架构师审计代码，发现 7 条会制造"错误确定性"的路径——从 Dashboard 今日餐次读取用 ?? 0 累加营养素，到日报/周报把不完整餐次汇总成确定摄入，甚至可能作为 LLM 输入放大错误确定性。同一天的数据在 Dashboard、活动详情页、Diet 主页三处可能给出相互矛盾的结论。

解法

新建 MealNutritionEvidence 深模块，定义 noMeals/incomplete/complete(Double) 三态，作为所有消费者的唯一读取入口，杜绝各处重复实现完整性判断。

协作插曲

05

ADR-001：为什么放弃"省事"的 items_json 方案

07-13数据建模决策

背景

MealRecord 原本只存一餐的营养汇总，每个食物的名称/克数/来源全部在保存后丢失——用户修正后重新打开会看到重新估算的结果，而不是自己保存过的分项。

被否决的两个方案

方案 A（加 items_json 列）："降低了眼前代码量，却把长期复杂度留给每一个消费者"——难以查询索引，JSON 解析会散落到各处。方案 C（立即建完整食品目录）："现在实施会把尚未验证的假设固化成核心 schema，属于过度设计"——没有确定的数据许可、版本策略和真实使用证据。

最终方案 B

meal_items 作为历史快照而非对可变食品目录的实时引用；provenance_kind/confidence/is_user_edited 记录来源与置信度；字段全部 nullable，汇总规则是"一餐有分项时，任一分项某指标未知，该指标就是 NULL，不是 0"。旧库从 v4 无损升级，117 个单测通过。

06

STAGE-008：主动删掉一个已经写在 schema 里的指标

07-14诚实边界

现象

sleep_efficiency 字段一直存在，但 DailyAggregator 只写 NULL，没有任何界面显示它——一条"无效且容易被未来误用"的隐式数据路径。真实审计 Simulator 库：98 条记录里 sleep_efficiency 非空 0 条，没有任何数据能验证这个算法。

根因

真实计算睡眠效率需要 inBed/asleep 成对夜间窗口，但当时代码回答不了 5 个关键问题：跨午夜一晚归属哪天、多来源同晚记录怎么选、缺 inBed 时是否该展示……

解法

保守方案——UPSERT 显式清除历史非空值，从卡片彻底删除这个展示项，只保留已验证的睡眠时长。测试证明清除效率没有破坏时长计算本身。宁可少一个功能，也不展示一个无法验证的数字。

07

STAGE-009 真机门抓出的具体缺陷：僵尸同步任务与"假删除"

07-15真机验收

僵尸同步任务

从真机数据容器审计出 sync_jobs 表里有 19 条 running 状态记录，最早遗留于 2026-06-10——这些不可能仍然有效，是跨进程/跨启动残留的僵尸任务。解法：新增 SyncJobRecovery，在任何同步/BGTask/observer 启动前，同一事务内把遗留的 pending/running 原子转 failed，且恢复失败时 fail-closed（不开放任何同步入口）。真机复跑验证：19 条全部转 failed，重复执行幂等。

HealthKit 营养"假删除"

syncMealNutrition 在四项营养全为空时直接返回，但底层删除函数返回值是 Void——调用方拿不到"删除是否真的成功"的信息，导致 SQLite 已清空但 Apple 健康里的旧样本仍然残留。解法：删除结果改为可观察类型，只有全部类型删除成功才清空本地同步标记，否则保留并向用户报告"检查 Apple 健康权限后重试"。

诚实标注的未完成项

后台 observer 增量同步有 845 个自然真机成功作业（横跨 40 天）作为证据，STAGE-009 判定 PASS；但受控的"手工在 Health App 增删 marker、观察响应"探针实验因本机钥匙串在锁屏状态下报错而未能完成——报告原文明确要求"不将自然事件证据表述为该受控探针"，没有把未完成的验证写成已完成。

五、双 AI 工具协作与治理协议

这个项目由 Claude Code 和 OpenAI Codex 两个工具协作开发，且 Claude Code 一度用 git worktree 拉出三条并行分支——这本身是一次"多 Agent 协作复杂产品开发"的真实样本。

并行分支3 条 worktree

great-thompson-f97a96（Round 8 稳定性修复 + Apple Health 风格仪表盘重写）、condescending-hoover-bb4b86（V2～V5 阈值/通知/相机/LLM 交付）、clever-swirles-86f66e（v7 活动能量口径+图表修复）分别完成后合并回 main。真实发生过一次分支心智混乱：dashboard 重写完成后用户第一次测试看不到新 UI，根因是仍在测试旧 main checkout 而新代码在独立 worktree 里，靠 git log 对比才定位。

Codex 的独立分工6 类工作

Tailscale + 本地 Ollama/oMLX 接入（纯 DevOps 配置）；LLM 多 provider 架构重构；oMLX 服务端诊断（需要直接读服务端日志的运维性调试）；发布/tag 纪律；Obsidian 项目库同步（把仓库状态写回用户的个人知识管理系统）；公开发布与微信小程序可行性评估（纯分析性任务，不改一行代码）。这些工作与 Claude Code 的连续功能迭代形成清晰的专业分工。

Architect-Coder 治理协议建立于 07-13

docs/planning/HEALTHMANAGER-ARCHITECT-CODER-WORKFLOW.md 确立了明确分工：架构师写 ADR/STAGE 任务书和自包含 Coder 提示词，Coder 只实现指定范围、不自行扩大、不提交/tag/push；架构师独立验收给出 PASS/FAIL/INCOMPLETE 三态结论，"总体状态取最弱子项"。文档还写明优先用更便宜的模型承担 Coder 角色，架构师角色本身用更强模型，且允许架构师在 Coder 表现不达标时直接接管——这条规则在 STAGE-007B（132k tokens 无 diff）里被真实触发过。

协作文化侧写

多份 Codex 会话记录反复出现用户原话"自己把整个项目连续进行到完成，包含测试和迭代部分"、"不要再问我了"——长期倾向于放权自主执行 + 事后验收的协作模式。35 天沉寂后重新拾起项目时，第一反应不是接着写功能，而是先把治理流程立起来，用协议替代逐次请示——这与沉寂前"连续 Round 式迭代"的松散节奏形成明显对比。

九、总结

64 天，35 天完全沉寂，剩下的 29 天里做完了从工程骨架到真机发布的全部工作——这条节律本身就是这份报告最诚实的一条线索：个人项目不靠匀速堆时间，而是在重新拾起时用治理纪律换回质量。Architect-Coder 协议、"总体状态取最弱子项"的验收原则、"不知道≠0"贯穿始终的数据纪律，共同构成了一种和纯粹"功能堆叠"完全不同的工程文化。

项目当前的诚实定位：一个尚未上架 App Store 的个人本地健康产品，不提供医疗诊断建议；它已经证明的，是消费级产品设计、本地数据架构、Apple 生态开发与真机验收闭环，可以由一个人在两个 AI 工具的协作下走完，并且工程纪律不缩水。
