# 健康管理类 App 竞品一手证据研究：薄荷健康、Elavatine 及相邻标杆

> 检索截止：2026-07-13（Asia/Shanghai）
> 研究范围：官方宣传与版本记录、隐私与监管披露、专利、论文/临床注册、App Store 元数据及原始评论。
> 目的：从可核验事实中提炼 HealthManager 下一轮可执行的迭代目标，而不是照搬竞品功能清单。

## 1. 结论先行

### 1.1 身份核验

- 用户提到的 **Elavatine** 拼写无误，对应中国区 App Store 的「Elavatine: 专业健身营养管理」，App ID `6503123667`，Bundle ID `com.lns.elavatine`。中国区服务提供者和隐私政策主体为深圳力冠实业有限公司。
- **薄荷健康**对应中国区 App Store App ID `457856023`，Bundle ID `com.boohee.food`；服务提供者和隐私政策主体为上海薄荷健康科技股份有限公司。上海市政府公开文件可核验其曾用名为上海薄荷信息科技有限公司。

### 1.2 两款产品真正值得学的部分

Elavatine 的优势集中在「高频记录效率 + 健身营养场景聚焦」：

1. 极简、无广告、弱社交的产品表面，减少记录干扰。
2. 围绕目标热量/宏量营养素，把“今天还剩多少”进一步转成“下一餐怎么吃”。
3. 最近食物、快捷复用、碳循环/训练部位标签等功能服务于高频健身用户。
4. 通过连续记录的摄入与体重趋势动态调整目标，而非永远依赖一次性 TDEE 估算——这个方向合理，但其算法精度宣传缺少公开验证。

薄荷健康的优势集中在「中国饮食覆盖 + 完整减重服务链」：

1. 长期积累的中餐、家常菜和包装食品搜索心智，降低中国用户记录门槛。
2. 体重、围度、饮食、运动、睡眠、设备数据、食谱、计划、课程、社区和商品形成完整闭环。
3. 最近版本把图片识别、自然语言记录、餐后反馈、餐次评分、下周菜单、睡眠趋势和用药背景逐步接入同一个 AI 助手入口。
4. 历史数据连续性和长期账户资产对老用户有很强留存价值。

### 1.3 对 HealthManager 的核心判断

HealthManager 当前已经具备两款竞品都不容易复制的底座：Apple Health 多源归因、数据质量对账、默认本地存储、无第三方分析、可选 LLM，以及确定性的日/周聚合。用户过去的实际反馈还明确了一个优先级：**活动能量和热量缺口的可信度比单纯增加功能更重要**；见 [WORKLOG.md](../../WORKLOG.md) 中“活动能量口径”一轮。

因此，HealthManager 的产品命题不应被改写成“又一个减肥 App”或“健美宏量营养工具”，而应保持为：

> **可信、私密、可纠正的个人健康闭环**：把多来源健康数据汇总清楚，在需要时低摩擦补录，并给出有依据、可解释、由用户掌控的下一步。

饮食是当前最值得补齐的高频短板，但不是产品的全部。最优先的动作不是先做更大的“AI”，而是先解决现有餐食分项未持久化的问题，再让饮食数据与现有活动、体重、睡眠、用药、来源质量和日/周趋势形成闭环。当前仓库明确记录：`meal_records` 只持久化总热量和三大营养素，AI 识别出的菜品 items 尚未保留；见 [NEXT_TASK.md](../../NEXT_TASK.md)。

### 1.4 竞品进入路线图的门槛

本文不以“竞品有、我们没有”为立项理由。任何候选能力必须同时回答五个问题：

1. **需求相关性**：是否改善已经明确的个人健康管理任务，而不是服务竞品的增长或商业模式？
2. **实际价值**：是否减少记录负担、提高数据可信度，或帮助理解已有数据？
3. **证据强度**：优势来自真实版本/用户行为/研究，还是只来自营销口号？
4. **边界兼容**：是否保持本地优先、无广告、无强社交、用户显式控制 AI？
5. **风险与成本**：在数据授权、医学边界、专利、数据库许可和维护成本上是否可接受？

由此，报告采用四类决策：**直接采用、转化采用、实验验证、明确排除**。技术机制可以学习，产品目标和交互不随竞品迁移。

## 2. 证据方法与边界

### 2.1 证据标签

本文将不同性质的内容明确分开：

| 标签 | 含义 | 可支持的结论 |
|---|---|---|
| 官方宣称 | 企业官网、App Store 文案、公司采访 | 证明企业正在这样宣传，不能单独证明效果或准确率 |
| 官方披露 | 隐私政策、版本记录、应用商店隐私标签 | 证明经营者或平台当前公开披露的功能/处理方式，不等于独立运行时审计 |
| 独立支持 | 政府监管文件、同行评审论文、临床注册、官方公共数据库 | 可支持相应范围内的事实，但仍需检查版本、样本和利益冲突 |
| 用户信号 | App Store 原始评论 | 可发现体验问题和需求措辞，不能估算总体发生率，也不能验证单条投诉真伪 |
| 合理推断 | 由多条证据共同导出的产品判断 | 用于制定假设，仍需在 HealthManager 中通过实验验证 |
| 未证实 | 未找到足够公开证据 | 不把“未找到”写成“不存在” |

### 2.2 来源质量分级

| 等级 | 来源类型 | 使用原则 |
|---|---|---|
| A | 政府/监管、同行评审全文或 PubMed、ClinicalTrials.gov、官方公共营养数据库、专利公开文本 | 用于核验实体、监管事实、研究设计和公开技术方案；专利不能证明产品采用或临床有效 |
| B | App Store 元数据/版本记录/隐私标签、产品隐私政策、官方帮助中心 | 用于确认当前公开功能和企业披露；不视为独立效果证明 |
| C | 官方营销页、公司口径报道、用户评论 | 只分析传播定位和体验信号，不能支撑效果、精度或市场规模的强结论 |

### 2.3 检索限制

- App Store 评分、版本和评论会持续变化；本文只记录 2026-07-13 的快照。
- 评论样本为中国区 App Store 最新 50 条，不是随机样本，也不代表全部用户。
- 专利以公开检索可定位的申请人为主；公司别名、关联公司或个人名下专利可能漏检。
- 本文没有执行抓包、二进制静态分析、SDK 运行时审计，也没有验证竞品服务器端算法。
- “没有找到论文/临床注册”只表示在本次品牌名精确检索范围内未识别，不等于绝对不存在。
- 小红书检索在本次环境中触发登录墙，因此没有把小红书帖子数量或情绪作为证据；B 站结果只用于发现讨论主题，未取得字幕的内容不参与结论编码。
- 第三方“测评”“软文”和营销案例只用于识别传播话术、商业目标与体验假设；凡是能用官方版本、政策、专利、论文或原始评论核验的，均以后者为准。

## 3. HealthManager 当前基线：先固定自己的需求边界

仓库当前说明显示，HealthManager 已经覆盖：

- 聚合 Apple Health 中 Garmin、米家、Apple Watch、华为和手动数据；
- 对体重、活动、心血管、睡眠、饮食等数据做同步、来源归因、质量对账和日/周总结；
- 可选 OpenAI-compatible LLM 做汇总评注和餐食图片营养估算；
- 本地 SQLite 存储，默认不上传健康数据，不接第三方分析或崩溃收集；
- LLM 只在用户主动配置后发送聚合摘要或主动选择的餐食图片。

以上均来自当前项目 [README.md](../../README.md)，属于本地代码库声明；是否与每个已安装版本完全一致，仍应在发布前用真机和网络行为复核。

当前最关键的产品债务是：

1. 餐食只持久化 calories/protein/fat/carbs 总量，识别出的菜品分项无法在以后完整编辑；
2. 饮食数据尚缺“来源、版本、可信度、份量依据、人工修订历史”等可审计字段；
3. 已有健康数据质量体系，但尚未把同样的可解释性延伸到营养识别和建议；
4. 导航、报告入口和睡眠效率表达仍有待整理。

因此，本轮竞品研究的价值在于补齐高频饮食闭环，而不是推翻已有架构。

### 3.1 从现有产品与历史反馈提炼出的“不变量”

| 已明确边界 | 本地依据 | 对竞品能力的约束 |
|---|---|---|
| 多源个人健康数据中枢 | [README.md](../../README.md) 的 Apple Health、Garmin、米家、Apple Watch、华为与手动数据链路 | 不退化成只管理体重和三大营养素的减脂工具 |
| 热量缺口可信度优先 | [WORKLOG.md](../../WORKLOG.md) 记录用户明确指出“热量缺口准确性最重要” | 任何目标、建议或 AI 都不能绕过摄入/消耗口径与数据完整度 |
| 默认本地、无第三方分析 | [README.md](../../README.md) 的隐私边界 | 不引入广告画像、默认云账户或无必要的行为 SDK |
| AI 由用户配置并显式触发 | 当前饮食编辑器以按钮启动多照片/文字估算，结果可逐项编辑 | 不把每次拍照自动上传，不以聊天界面取代确定性功能 |
| 饮食、用药、活动、睡眠、来源质量并存 | 当前五个主 Tab 与二级页面 | 竞品的纯减脂或纯健美能力只能按需转化，不能主导整体信息架构 |
| iPhone 优先 | [WORKLOG.md](../../WORKLOG.md) 已明确撤回 iPad 支持 | 优先 Apple 原生快捷记录、组件和 HealthKit，不追求多端平台化 |
| 长期趋势保留日级真实度 | 历史版本按用户反馈恢复年视图每日点，只简化轴标签 | 不能为视觉“整洁”牺牲用户重视的原始时间分辨率 |

### 3.2 本产品真正要完成的五类任务

1. **看清现在**：今天的体重、活动、摄入、消耗、睡眠、用药和数据缺口是什么状态。
2. **补齐事实**：外部数据没同步或饮食无法自动获得时，能快速补录并纠正。
3. **相信数字**：知道数值来自哪个设备/数据库/AI、是否重复、是否完整、误差可能在哪里。
4. **理解趋势**：把日级数据放回周/月/年的个人上下文，但不把相关性说成因果。
5. **采取一小步**：在证据足够时给一条可执行建议；证据不足时坦白显示“未知/等待更多数据”。

这是后文筛选所有竞品优点的基准。

## 5. Elavatine 深入分析

### 5.1 官方定位与功能

官方 [Elavatine 网站](https://elavatine.com/) 和 [App Store 页面](https://apps.apple.com/cn/app/id6503123667) 共同呈现的产品主线是：

- 为健身人群和教练提供热量与宏量营养素追踪；
- 记录食物、体重、体脂、围度、饮水、活动和训练相关标签；
- 根据持续数据动态调整代谢/目标；
- 根据当天剩余目标给出下一餐建议和替换方案；
- 支持碳循环、训练部位标签及日目标调整；
- 强调界面简洁、无广告、无社交干扰。

版本记录还显示它正逐步把静态记录改造成连续教练：

- 2.3.1：AI 食物搜索、下一餐建议、碳循环与训练部位标签、目标置顶；
- 2.3.2：单日碳循环目标调整、力量训练标签和营养总结；
- 2.3.8：日志注释标签能力；
- 之后的版本继续强化记录和订阅体系。

这类版本记录比首页营销文案更能证明功能确实曾经进入公开发行版本，但仍不能证明算法效果。

### 5.2 营养数据库宣传的核验

Elavatine 官方声称食物数据参考 USDA 和“香港卫生署”。公开来源核查后应作如下修正：

1. 美国 [USDA FoodData Central](https://fdc.nal.usda.gov/about-us/) 确实是权威公共食物营养数据库，并提供不同来源和质量层级的数据下载；见其 [下载与版本页](https://fdc.nal.usda.gov/download-datasets/)。
2. 香港公开的营养资料库实际由香港食物环境卫生署食物安全中心（CFS）维护，而不是“香港卫生署”；[CFS 营养资料查询系统](https://www.cfs.gov.hk/english/nutrient/index.php/fc-introduction.php) 覆盖能量及多项营养素，并引用多个地区数据源。
3. 权威来源名称不能自动证明 App 内每条记录、份量换算、去重合并或本地菜品映射准确。
4. 本次未发现 Elavatine 公开其数据版本、ETL 规则、覆盖率、冲突处理、抽样审计或误差报告。
5. CFS 页面对数据使用范围有明确说明；Elavatine 是否取得适用于商业产品的许可未能从公开材料核验。这里应列为合规尽调事项，不能据此断言侵权。

对 HealthManager 的直接启示是：不要只在关于页面写“数据来自某权威库”，而应在每条食物上展示来源、版本日期、营养素覆盖、份量依据和是否经人工校验。

### 5.3 “动态代谢模型”宣传与科学边界

Elavatine 官网使用了非常强的准确性话术，并表示算法由职业运动员和营养专家参与设计，但没有公开以下关键证据：

- 参与者姓名、资质或利益关系；
- 方程、输入变量、校准周期和不确定性；
- 独立验证数据集、误差分布或人群限制；
- 特殊人群和异常状态的安全边界；
- 同行评审论文、临床注册或外部审计。

“根据摄入和体重趋势动态估计能量消耗”在科学上是合理方向。美国 NIDDK 的 [Body Weight Planner 研究说明](https://www.niddk.nih.gov/research-funding/at-niddk/labs-branches/laboratory-biological-modeling/integrative-physiology-section/research/body-weight-planner) 和相关 [Lancet 模型论文](https://pubmed.ncbi.nlm.nih.gov/21562087/) 展示了公开方程、适用范围和验证边界；另一项 [人体能量平衡模型验证研究](https://pubmed.ncbi.nlm.nih.gov/20962159/) 也报告了可量化的预测误差。它们可以支持“动态模型值得做”，但不能替 Elavatine 的专有实现背书。

结论：Elavatine 的算法主张目前属于“官方宣传、概念上可行、品牌级效果未证实”。HealthManager 若采用相似方向，应公开“数据够不够、为什么改目标、预期误差多大、哪些情况下不建议使用”，避免绝对化精度措辞。

### 5.3.1 对强营销话术逐项校验

### 6.4 学术论文与临床证据

品牌名精确检索结果：

- PubMed 中 `Boohee` 可定位 2 篇直接相关记录；`Elavatine` 为 0；
- ClinicalTrials.gov 中两个品牌名精确检索均为 0；
- 未找到可直接证明任一品牌整体减重效果的公开随机对照试验。

薄荷相关的两篇论文是：

1. [Understanding and Predicting the Adoption of Fitness Mobile Apps](https://pubmed.ncbi.nlm.nih.gov/32041437/)：研究 8,840 名薄荷用户的 30 天饮食、运动、体重和登录行为，重点是使用采纳和持续使用因素。它能支持“行为数据可预测留存/采纳”，不能证明减重效果。
2. [Food Atlas 开发研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC11607570/)：把薄荷作为对照产品之一，论文表格记录了研究当时的关键词搜索、配料、烹饪方式和营养信息等能力。该快照早于当前图片 AI 功能，也没有验证薄荷食物数据精度或临床结局。

PubMed 之外，CIKM 2017 论文 [Understanding and Predicting Weight Loss with Mobile Social Networking Data](https://doi.org/10.1145/3132847.3133019) 明确使用 BOOHEE 的 9,967,290 名用户数据，发现个人因素和社交活动与减重状态相关，并构建预测模型。它能证明薄荷在当时拥有大规模可研究数据，也说明社交活动可能包含预测信号；但它是历史观察性数据挖掘，不是随机干预，不能证明社区导致减重，更不能证明 2026 年活跃用户规模。

这个结果不会改变 HealthManager 的产品边界：本项目没有必要为了利用“社交信号”而增加公开社区。更适合的转化是用**个人自己的连续记录、修订历史和完成度**形成反馈信号，保持隐私与单人使用体验。

相邻产品 Noom 的证据提供了一个更高标准参照：2026 年发表的 [随机对照试验](https://onlinelibrary.wiley.com/doi/full/10.1002/osp4.70122) 比较数字行为干预与教育对照，报告了 16 周和 68 周的组间体重差异；研究已在 [ClinicalTrials.gov](https://clinicaltrials.gov/study/NCT06666842) 注册。需要同时注意：研究由 Noom 资助，多名作者与公司有雇佣或持股关系；它验证的是包含自我监测、心理教育、教练和群体支持的整套方案，不是某个界面控件或 AI 功能。

对 HealthManager 的要求应因此提高：如果以后宣传“帮助减重”或“改善指标”，应预先注册研究、定义主要终点、公开流失率和不良事件，并把算法准确性与健康结局分开验证。

### 6.4.1 行为研究对功能优先级的真实含义

相邻研究对路线图提供了三个比“竞品有 AI 教练”更可靠的判断：

1. MyFitnessPal 参与的 [GoalTracker 随机试验](https://pubmed.ncbi.nlm.nih.gov/30816851/)（n=105）三组在 3 个月的体重变化没有显著组间差异，且研究再次记录到饮食自我监测会快速衰减。它不证明某个 App 单独有效，但支持先降低记录摩擦，而不是先堆课程。
2. [简化记录与标准热量记录的试点随机试验](https://pubmed.ncbi.nlm.nih.gov/35146942/)（n=72）在 6 个月均有减重，组间差异不显著。对产品的合理启示是提供“快速估算”和“精确分项”两种负担等级，而不是强迫每餐都达到研究级完整度。
3. [SMARTER 随机试验](https://pmc.ncbi.nlm.nih.gov/articles/PMC9297147/)（n=502）中，基于自我监测数据的每日定制反馈没有带来相对自我监测单独组的显著额外减重；打开消息的参与度与结果相关，但这仍不能证明消息本身的因果效果。因而，泛化 AI 建议或高频推送不应先于可靠记录与用户主动查看。

综合来看，研究支持的是“**让用户愿意持续记录，并在需要时得到恰当反馈**”，不是“聊天越多越健康”。

负向信号：

- 广告干扰、跳转和界面拥挤；
- 基础能力进入付费墙后的价值争议；
- 订阅、退款和挑战活动相关投诉；
- AI 热量识别错误；
- 同步、登录、相机、性能和稳定性问题。

有一条 5 星评论正文仍在批评广告，说明不能只按星级做情感分析。近期差评密度也不能用来推翻其长期累计评分；两个统计回答的是不同问题。

### 6.7 薄荷健康可借鉴与不可照搬

可借鉴：

- 对中国菜、家常菜和本地包装食品的长期结构化覆盖；
- 记录后立即反馈，以及下一步建议；
- 餐次评分、复制/批量编辑、下周菜单和多设备接入；
- 把饮食、体重、睡眠、活动和用药放进一个连续助理上下文；
- 让用户多年历史数据形成可迁移、可复用的个人资产。

不可直接照搬：

- 广告、电商、社区、医疗和工具全部挤进核心记录流；
- 用选择性累计指标替代效果证据；
- 基础记录能力过度付费化导致的信任损耗；
- 大量敏感数据和第三方链路，却缺少用户可见的逐次数据流说明。

### 6.8 广告、软文和商业案例告诉了什么

营销案例不是效果证据，但能解释产品为什么变成现在的形态。2022 年一篇[电商营销案例](https://i.ifeng.com/c/8DvBIU1RbkD)把薄荷描述为“小红书种草—微信/抖音曝光—多平台电商转化—App/私域沉淀”的全链路，并以订单、销售额、注册用户和 ROI 为成功指标。薄荷当前 App Store 文案同时展示社区、成功故事和薄荷商店，说明这套商业方向确实进入了产品表面。

再与 2026 年 App Store 原始评论交叉看，可得出一个有限但重要的判断：**电商和广告扩张实现了商业闭环，却也让一部分长期用户感到核心记录被打断。** 这不能证明商业化必然伤害体验，但足以把“广告、电商、内容流量”从 HealthManager 的产品路线中排除。

第三方 [MWM 评论聚合页](https://mwm.ai/apps/ai/457856023)也概括了广告、付费墙、食物覆盖和 AI 准确性争议，但它的自动摘要、市场口径和更新时间不可控，因此本文只把它作为对 Apple 原始评论主题的二次印证，不使用其下载量或排名作为事实。

## 7. 相邻标杆：同类 App 的可迁移优点

这一节不把全球产品当成中国市场的直接替代，而是用官方帮助中心或公开研究提取“可迁移设计”。

### 7.1 MacroFactor：可解释的动态目标

官方帮助说明其 [能量消耗估计](https://help.macrofactorapp.com/en/articles/20-expenditure) 基于持续记录的摄入与趋势体重，数据不完整会影响估计；目标按周期更新，并通过平滑和护栏减弱水分波动影响。其 [食物数据库说明](https://help.macrofactorapp.com/en/articles/46-food-search-database) 还区分大规模验证条目与营养素更完整的研究级条目。

可迁移点：

- 把模型输入、数据完整度和调整原因展示给用户；
- 先平滑体重趋势，再做周级目标调整；
- 允许 coached、collaborative、manual 等不同控制程度；
- 对碳循环等策略保持“支持记录但不夸大证据”的中立态度。

### 7.2 Cronometer：数据来源和营养素质量

Cronometer 的 [数据来源说明](https://support.cronometer.com/hc/en-us/articles/360018239472-Data-Sources) 为食物条目标记来源和质量，区分实验室分析与标签数据库；[Data Confidence Score](https://support.cronometer.com/hc/en-us/articles/360042550452-Data-Confidence-Scores) 进一步把营养素完整度和数据来源转成用户可见的信心等级；其 [设备集成说明](https://support.cronometer.com/hc/en-us/articles/360024748771-Mobile-Integrations) 明确提醒多来源同步可能造成重复计数。

可迁移点：

- 每条食物都能回答“来自哪里、何时更新、有哪些营养素”；
- 给实验室/官方、包装标签、用户自建、AI 估算不同质量等级；
- 设备同步时主动检测重复来源；
- 从宏量营养素逐步扩展到微量营养缺口，但不伪造缺失值。

### 7.3 MyFitnessPal：入口广，但数据质量要分层

官方 [Meal Scan 说明](https://support.myfitnesspal.com/hc/en-us/articles/360045761612-Meal-Scan-FAQ) 和 [Premium 功能页](https://support.myfitnesspal.com/hc/en-us/articles/360032625951-What-are-the-features-of-MyFitnessPal-Premium) 展示图片、语音、条码、餐次/每日目标和导出等多入口。其 [验证标记说明](https://support.myfitnesspal.com/hc/en-us/articles/360032273292-What-does-the-check-mark-mean) 同时承认，即使有验证标记也可能存在错误；用户提交条目尤其需要纠错机制。

可迁移点：

- 图片、语音、条码、标签 OCR 和文字搜索都只是“候选生成器”；
- 最终保存前必须让用户看见并修改食物、份量和营养值；
- 大数据库不等于高质量数据库，要展示验证等级和纠错入口。

### 7.4 YAZIO：把 AI 的不确定性说清楚

YAZIO 的官方 [AI 识别帮助页](https://help.yazio.com/hc/es/articles/39137901903889--Qu%C3%A9-es-la-nueva-funci%C3%B3n-de-IA-y-c%C3%B3mo-funciona) 明确说明识别是近似值，不保证完全准确，并要求用户复核/编辑食材与份量，之后可保存为模板。

可迁移点：

- 不把 AI 估算包装成测量值；
- 展示置信度、缺失配料和份量假设；
- 一键修订后保存为个人模板，让一次人工校正产生长期价值；
- 餐食评分避免简单贴“好/坏”标签，支持弹性周末和计划日。

### 7.5 FoodNoms：最接近本项目边界的 Apple 原生路线

FoodNoms 的[官方产品原则](https://foodnoms.com/help/about-foodnoms/)强调少干扰、无侵入广告、基于时间和历史的智能建议、条码、AI 辅助、Apple Health、Shortcuts、组件和 Apple Watch。它的优势不在于做一个庞大健康平台，而在于把“重复记录”变成 Apple 生态内的短动作。

可迁移点：

- 根据本人的时间和历史记录排序候选，而不是建立公共社交推荐；
- 用 Shortcut、组件或 Watch 快速补录，完成后仍进入统一、可审计的数据模型；
- AI 只是候选生成，用户历史修订才是越来越好用的个人资产；
- 产品保持安静，把工具效率而不是内容消费作为留存机制。

需要注意：FoodNoms 的“隐私优先”不等于完全本地，HealthManager 不应直接复制其云端设计，而应复用交互思想。

### 7.6 Noom：行为干预必须作为整体验证

Noom 的优势不是营养数据库，而是把自我监测、短课、心理教育、教练和群体支持组合成行为改变方案。其已发表随机试验提供了比普通 App 宣传更强的证据，但存在企业资助和作者利益关系，且证据对应整套干预。

可迁移点：

- 把反馈设计成短小、及时、可执行的行为提示；
- 让用户回顾触发因素、情绪和环境，而不只看热量；
- 若引入教练/课程，应把其作为完整干预评估，不能把整体试验效果归因到单一 AI 功能。

### 7.7 Keep 等综合健身平台：能力优秀，但产品目标不匹配

Keep 的[官方公司介绍](https://ir.keep.com/sc/about_profile.php)把 AI 辅助训练计划、直播/录播课、设备、装备、服饰和食品定义为一站式健身生命周期。它证明“运动内容—训练执行—设备数据”可以形成完整生态；但 HealthManager 当前的任务不是提供海量课程或争夺健身内容时长。可借鉴的是把已有运动记录与恢复/饮食上下文关联；课程商城、直播、社区挑战和硬件销售均不进入近期路线。

## 8. 面向 HealthManager 的产品决策，而不是竞品功能清单

### 8.1 采用 / 转化采用 / 实验验证 / 排除

| 竞品优点或行业机制 | 对本项目的真实价值 | 决策 | 在 HealthManager 中应怎样落地 |
|---|---|---|---|
| Elavatine 的最近记录、克数记忆、整餐/选中项复用 | 直接降低每天记录成本 | **直接采用** | 最近餐、常用项、收藏模板、复制整餐/选中项、跨餐次移动；继续保持显式保存 |
| 薄荷的中餐/包装食品覆盖 | 解决 AI 估算缺少可校验基准的问题 | **转化采用** | 不复制其封闭库；先建立来源/许可清楚的数据接入层，再逐步补中国常见食物与个人食品 |
| Cronometer 的来源与 Data Confidence | 与现有来源归因、数据质量理念高度一致 | **直接采用** | 每个食物/营养值显示来源、版本、完整度、人工修订和置信级别 |
| Elavatine/薄荷的“今日剩余”和下一餐建议 | 能把数据变成行动，但默认目标未必符合用户需求 | **转化采用** | 先展示已摄入、已消耗、当前缺口和数据完整度；目标与下一餐建议必须由用户选择开启 |
| MacroFactor/Elavatine 的趋势能量模型 | 有机会提高长期消耗估计，但公开证据和本项目数据量尚不足 | **实验验证** | 先以影子模式计算，不改当前缺口、不自动改目标；与现有 HealthKit 口径比较后再决定 |
| FoodNoms 的 Shortcuts/组件/Watch 快速入口 | 符合 iPhone-only、个人高频使用 | **转化采用** | 先做快捷补录/复制上一餐和今日概览，不为“多端覆盖”引入账号平台 |
| 薄荷 AI 助手连接记录、计划和反馈 | 结构化操作比纯聊天有价值 | **转化采用** | AI 只能调用可审计的本地动作或生成候选；关键数值仍由确定性计算与用户确认产生 |
| Noom 的课程、教练和行为干预 | 对部分人有效，但远超当前单人健康数据工具边界 | **实验验证/远期** | 如有真实需求，仅试一条事件触发的短提示；不先建课程中心或聊天教练 |
| 薄荷社区、挑战、成功故事 | 与当前个人、私密工具目标偏离 | **明确排除** | 不做公开动态、排行、打卡广场或“他人成功”压力 |
| 薄荷电商、广告、内容流量闭环 | 服务商业转化而非本项目核心任务 | **明确排除** | 不做开屏广告、商城、代餐导购、软文信息流 |
| Keep 式完整训练课程/直播 | 已有运动数据的解释有价值，课程供给没有 | **明确排除近期** | 只做现有训练、恢复、饮食的上下文，不建设内容平台 |
| 激进订阅墙 | 会伤害长期个人数据资产的可信与可迁移性 | **明确排除** | 基础录入、修订、历史、导出、删除不锁死；当前也没有立项商业化的必要 |

### 8.2 产品体验主线：今天先回答四个问题

下一版不应让首页变成减脂课程首页。更符合本产品的“今日”体验是：

1. **数据齐不齐**：哪些来源已同步，哪些关键数据缺失或冲突。
2. **今天发生了什么**：体重、睡眠、活动、摄入、消耗、当前热量缺口和用药状态。
3. **哪些数字可信**：实测、设备估算、数据库、用户输入和 AI 估算分别标识。
4. **现在最值得做什么**：最多给一条有依据的行动；没有足够依据时不强行建议。

这条主线会吸收竞品的“剩余额度/下一步”优点，但仍然服务于 HealthManager 的多源健康任务，而非把所有健康指标压缩成体重目标。

### 8.3 建议下一迭代（v0.3）：可信记录基础，不追求功能数量

#### A. 餐食分项正式持久化

- 新增版本化迁移，优先采用规范化的 meal items 结构；仅用一个 items JSON 可以作为过渡，但不应阻断后续搜索、复用、来源和统计。
- 每个 item 至少保存：名称、克数/份量/单位、生熟状态、热量和三大营养素、来源类型与 ID、来源版本、识别方式、置信度、用户是否修订、修订时间。
- 现有餐次总量和照片无损迁移；总量保留快照，同时可由分项重算并发现不一致。

这是所有食物搜索、复制餐次、标签 OCR、营养趋势和可信 AI 的共同地基，也是当前 [NEXT_TASK.md](../../NEXT_TASK.md) 已确认的真实缺口。

#### B. 把“重复记录”做快

- 最近餐次、最近食物、常用克数和收藏模板；
- 复制整餐或选中菜品，支持跨早餐/午餐/晚餐移动；
- 用户修正过的菜名、份量和营养值优先于公共候选；
- 保留当前照片 + 文字 + 手工录入，AI 仍由用户点“AI 估算营养”后运行；
- 提供“快速估算”和“精确分项”两种深度，最终都落到同一数据模型。

体验目标可以先定为“重复餐不超过两次主要操作即可进入确认”，但首发前仍需用真机任务计时确认是否现实。

#### C. 延伸现有数据质量能力到饮食

- AI 识别只负责生成食物/份量候选，营养值优先匹配有来源的条目；找不到匹配时明确显示“AI 估算”。
- 分开显示：官方/实验室数据库、包装标签、用户自建、AI 估算，不用一个笼统的“准确”徽章。
- 对能量与三大营养素关系、单位、重复项、极端份量和 HealthKit 往返写入做本地异常检查。
- 用户每次修正都可以保存为个人模板，但不自动上传形成公共数据库。

#### D. 整理导航，但保留产品全貌

当前“来源”和“同步中心”属于必要基础设施，却长期占据两个一级 Tab；“报告”和“设置”入口较深。建议原型验证：**今日 / 饮食 / 用药 / 趋势 / 更多**。来源、同步、数据质量和设置归入“更多”或今日状态的下钻，不删除任何诊断能力。

这只是待验证的信息架构，不应在没有原型试用前直接重写。现有 [NEXT_TASK.md](../../NEXT_TASK.md) 还列有睡眠效率误读和图标收尾；v0.3 应顺手解决睡眠效率的“正确计算或隐藏”，避免新功能盖住旧数据表达问题。

### 8.4 后续迭代（v0.4）：有来源的食品数据与个人记忆

1. **食品来源层**：先接许可清晰、可版本化的数据。USDA FoodData Central 的 [API 指南](https://fdc.nal.usda.gov/api-guide/)说明其数据为 CC0 公共领域；中国食物成分表、香港资料和商业包装库需在接入前逐项确认许可，不能直接抓取竞品数据。
2. **标签 OCR / 条码**：用于生成包装食品候选，必须保存标签照片、每份/每 100g 口径和人工确认；条码命中不是准确性证明。
3. **个人纠正记忆**：同一餐厅、菜品或包装食品再次出现时优先复用本人最后确认的数据，这是比“百万级公共库”更符合单用户产品的长期优势。
4. **Apple 原生快捷入口**：Shortcut / App Intent、组件和可选 Watch 快速动作，优先覆盖“复制上一餐、快速补录、查看今日缺口”。
5. **日报/周报行动化**：从长段 AI 评语转为一条证据卡，显示使用的数据、缺失项和为什么建议；本地确定性总结仍是默认。

### 8.5 有意义但必须先验证的探索（v0.4 影子实验）

#### 探索 1：个人能量消耗校准

- 输入只使用用户已经确认的摄入、趋势体重和现有活动/基础代谢数据；
- 先离线回放历史，再在 App 内以 shadow mode 运行；
- 与当前“基础代谢 + 活动能量 − 饮食摄入”并列比较，不改正式热量缺口，不自动下调目标；
- 数据不足、体重波动异常、摄入缺失或用药/疾病可能干扰时必须进入“保持/暂停”状态；
- 最低数据天数、完整度和护栏幅度必须从本机历史与回放结果选择，不能照抄竞品的固定数字。

#### 探索 2：个人食物记忆，而非公共推荐流

- 根据时间、地点（仅在用户允许且确有价值时）、历史餐次和本人修正排序候选；
- 所有学习在本地完成；提供“为什么排在前面”和清空个人记忆；
- 衡量重复餐完成时间、修订次数和次日复用率，而不是推荐点击率。

#### 探索 3：跨域“相关性提示”

- 探索睡眠、活动、饮食、体重和用药日志在本人历史中的时间关系；
- 只写“同期出现/值得观察”，不写“某食物导致睡眠变差”；
- 样本不足、数据源改变或缺失时不出结论；用户可查看原始日期点。

#### 探索 4：一条可行动的今日简报

- 不是开放式 AI 聊天，而是从确定性规则挑选最值得处理的一项：补同步、补一餐、确认异常数据、完成用药记录或查看趋势；
- 用户可关闭或稍后处理；不使用连续推送制造焦虑；
- 用完成率、被关闭率和“是否帮助理解数据”的主观反馈判断价值。

### 8.6 只有实验通过后才进入的 v0.5 候选

- 用户主动设置的热量/宏量目标及下一餐建议；
- 微量营养素覆盖（只在来源完整时计算，缺失值保持未知）；
- 训练日/休息日模板、食谱和采购清单；
- 轻量饥饿/情绪/场景反思；
- 家庭或专业人士共享，但必须逐项授权且默认关闭。

碳循环、16:8、固定减重法等可以作为用户自选模板，不应成为 HealthManager 的默认方法论。

### 8.7 明确不进入当前产品方向

- 公开社区、排行榜、成功故事流和社交压力；
- 广告、电商、代餐导购、直播课程和泛健康内容中心；
- 以“冠军算法”“绝对精准”“几秒必完成”作未经测试的宣传；
- 自动诊断、自动用药建议或根据短期波动自动改变治疗/用药；
- 在数据不足时仍给出确定目标，或把设备估算消耗包装成实测 TDEE；
- 为扩功能而默认注册账号、上传历史健康数据或引入第三方追踪 SDK。

### 8.8 下一迭代的验收边界

- 旧餐次迁移无丢失，已有照片、总量和 HealthKit 同步关系保持；
- 新餐次保存后可重新打开并逐项编辑，分项与总量关系可校验；
- 手工、AI、以后加入的 OCR/条码走同一模型，每个营养值可追溯来源；
- AI 未配置、关闭或离线时，手工记录、历史复用、报表和现有健康链路仍完整可用；
- 用户修正不会被下一次 AI 结果静默覆盖；
- 热量缺口继续明确显示当前公式及数据完整度；任何影子模型不改变正式结果；
- 不新增广告、第三方分析或默认云上传；
- 建立一组经称量的中国常见餐食基准，先记录现有 AI/数据库基线，再据数据决定误差门槛，不预先编造“准确率 95%”之类指标；
- 导航原型通过真实日常任务验证后才替换现有 Tab。

以上路线的顺序是：**先让数据可保存、可复用、可追溯，再让模型越来越聪明；先服务现有需求，再决定探索是否值得产品化。**

## 9. 建议的验证计划

### 9.1 食物数据库

- 建立中国常见菜、混合菜、外卖、包装食品和家常份量的金标准样本；
- 分开评估：食物识别准确率、食材遗漏率、份量误差、热量误差、宏量误差和微量营养素覆盖；
- 报告中位误差、分位数和失败样例，不能只报平均准确率；
- 对每次数据库更新保留版本和回放测试。

### 9.2 动态目标

- 先离线回放历史记录，验证数据缺失、体重水分波动、极端摄入和设备重复等边界；
- 先与现有公式做影子比较；在没有通过误差、稳定性和可解释性门槛前，不改变用户正式看到的缺口或目标；
- 根据回放基线定义数据完整度、暂停条件和允许变动范围，不照搬竞品阈值；
- 对每次调整保留可审计原因；
- 在宣传任何健康效果前，至少开展前瞻性试点，再根据风险决定是否做注册试验。

### 9.3 体验与可靠性

- 计时任务：记录一顿重复早餐、一顿混合中餐、一份包装食品和一顿照片识别餐；
- 追踪保存成功率、修订次数、完成时间和次日复用率；
- 对离线、杀进程、HealthKit 延迟、多设备重复和 LLM 超时做故障注入；
- 对“今日一条建议”、AI 估算和异常提示分别监测查看、关闭、修订和信任反馈，避免用点击率替代真实帮助。

## 10. 不应做出的结论

根据当前公开证据，以下说法都不严谨：

- “Elavatine 的 TDEE 毫无误差”——没有公开方程、验证集或误差报告。
- “薄荷健康有专利，所以减重有效”——专利不等于当前实现，更不等于临床效果。
- “薄荷有 1.8 亿用户，所以食物数据一定准确”——规模与数据质量是两件事。
- “最近 50 条评论差评多，所以整体用户都不满意”——样本非随机且存在时间窗口偏差。
- “没有检索到 Elavatine 论文/专利，所以一定没有”——只能说本次精确检索未识别。
- “隐私政策写了某项能力，所以实际一定合规”——仍需当前版本运行时审计。
- “AI 看图识别的热量就是摄入量”——最多是带假设的估算，必须允许复核和修订。

## 11. 尚未证实、下一步需要补证的事项

1. Elavatine 动态代谢模型的方程、误差、校准周期、训练数据和特殊人群边界。
2. Elavatine 使用 USDA/CFS 数据的具体版本、授权、清洗和商业使用范围。
3. 两款 App 当前 iOS 版本的实际网络请求、SDK 启动条件、照片保存位置和删除效果。
4. 薄荷健康 2025 年 Android 隐私通报后的整改状态，以及是否影响其他平台版本。
5. 薄荷食物库当前“百万级”条目的去重、过期包装食品治理和营养素缺失率。
6. 两款产品“AI 图片识别”和“体重预测”的公开准确率、外部验证及失败保护。
7. 评论中关于扣费、退款、崩溃和数据丢失的真实发生率；需要更长时间窗、版本分层和客服工单才能估计。
